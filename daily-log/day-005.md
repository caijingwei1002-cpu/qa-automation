## 学习记录

今天理解了：等价类把预期行为相同的输入归为一类，边界值关注规则发生变化的位置。空白输入代表去除空格后有效长度为 0 的无效边界；前后空格代表输入规范化风险；重复文本代表重复数据规则；长文本代表健壮性输入。没有明确最大长度规格时，256 字符是代表性长文本，不宣称是系统最大边界。

它解决的问题：避免只用正常文本测试而漏掉空输入、规范化、重复记录和长文本处理问题，也避免使用会掩盖缺陷的宽松断言。

我实际如何使用它：新增四个独立测试，分别断言空白输入创建 0 条、带首尾空格的输入创建 1 条且 `textContent` 精确为 `Buy milk`、重复输入创建 2 条且集合文本完整匹配、256 字符输入创建 1 条且文本未被截断。

遇到的问题：前后空格场景如果使用普通字符串形式的 `to_have_text("Buy milk")`，断言会进行空白规范化，无法严格区分应用是否真的去除了首尾空格；编辑过程中还发现过尾随空格和顶层函数间距问题。

根因或当前假设：断言语义比预期更宽松，可能把 DOM 中仍保留空格的实现判为通过。通过 `to_have_js_property("textContent", "Buy milk")` 检查原始 DOM 属性，并通过 `git diff --check` 和格式复检修复了代码格式问题。假设当前 TodoMVC 产品规则允许重复文本且没有 256 字符上限；本次运行结果支持这些预期。
