## 今日学习与产出

- 通过需求讨论明确：匹配 booking 和干扰 booking 只在当前过滤字段上有明确差异，其他字段尽量保持一致。
- 在 `test_filters.py` 中为 firstname、lastname 和 checkin 场景生成自有匹配/干扰资源，验证匹配资源包含、干扰资源排除，并回查返回详情。
- 创建成功后立即提取并保存两个 `bookingid`，使用 `finally` 分别清理，删除后再次 GET 验证 404。
- 将相同的数据隔离与清理模式迁移到 `test_get_bookings.py`，验证无过滤集合包含两个当前测试创建的 booking。
- 重启本地服务后重复目标和全量测试，结果保持一致。

## 实验前问答

问题 1：匹配资源和干扰资源应该如何设计？
回答：只在当前过滤字段上命中与不命中目标值，其他字段尽量保持一致，避免其他差异掩盖过滤条件失效。

问题 2：为什么必须用创建响应返回的 `bookingid` 追踪资源？
回答：业务字段可能重复或被其他测试使用，创建响应中的 ID 才是本次创建资源的稳定身份，也是清理资源的准确依据。

问题 3：如何验证服务重启前后行为一致？
回答：重复相同的输入和过滤条件，比较本测试创建资源的包含/排除关系；共享服务中的其他资源可能变化，不能只用整个集合相等作为依据。

## 学习记录

今天理解了：过滤测试的输入必须由测试自己控制，至少构造一个匹配资源和一个干扰资源，并用动态 ID 验证集合的包含与排除。

它解决的问题：避免测试依赖共享环境中的固定 booking。服务重启、数据库重置或其他测试改变预置数据时，固定字段查询会产生脆弱失败或假通过。

我实际如何使用它：在 `test_filters.py` 中按过滤字段生成两份数据，创建后立即登记 ID，查询时断言匹配 ID 出现、干扰 ID 不出现，再回查详情验证所有返回资源的过滤字段。清理阶段分别处理两个 ID，并检查删除后的 404。在 `test_get_bookings.py` 中迁移同样模式，验证无过滤集合包含两个自建 booking。

遇到的问题：独立迁移初始编辑时把集合查询放在资源创建之前，且函数签名和格式暂时不完整。

根因或当前假设：迁移时先插入了验证逻辑，未先整理 setup、业务验证和 teardown 的控制流。重新按“认证 → 生成数据 → 初始化 ID → try 创建与验证 → finally 清理”排列后，目标测试通过。
