## 实验前问答

问题 1：为什么不能只用一个 Schema 同时描述 POST 创建响应和 GET 详情响应？
回答：两者顶层结构不同：POST 响应包含 `bookingid` 和 `booking` 包装对象，GET 响应直接返回 booking。强行共用会导致过宽或验证失败；应复用资源定义，再分别定义响应 envelope。

问题 2：`required`、`properties`、`type` 和 `additionalProperties` 分别解决什么问题？
回答：`required` 约束字段必须存在，`properties` 描述字段规则，`type` 约束数据类型，`additionalProperties` 控制未声明字段是否允许；四者分别覆盖存在性、定义、类型和额外字段。

问题 3：Schema 验证通过，能否证明 `checkout` 一定晚于 `checkin`？
回答：不能。Schema 可以验证两个日期字段存在、类型为 string 且格式合法，但 `checkout > checkin` 是跨字段业务关系，需要单独的业务断言。

## 学习记录

今天理解了：

JSON Schema 用声明式规则验证响应的结构契约，包括字段存在性、类型、嵌套对象、日期格式和额外字段；它不能替代跨字段业务规则。

它解决的问题：

把散落在测试中的 `in`、`isinstance` 和嵌套键访问统一为可复用结构验证，及时发现响应缺字段、类型变化或额外字段，降低接口演进时的静默破坏风险。

我实际如何使用它：

新增 `schemas/booking.json`，用 `$defs` 复用 booking 结构，分别覆盖 POST 创建 envelope 和 GET 详情响应；通过 `Draft202012Validator`、`FormatChecker` 和 `$ref` 接入两个真实测试，并用合成变更验证缺失字段和类型变化会失败。

遇到的问题：

初次运行因虚拟环境缺少 `jsonschema` 在收集阶段失败；安装依赖后 Schema 测试和创建/查询测试通过。全量仍有两个过滤测试找不到固定 `Jim/Brown` 数据。

根因或当前假设：

依赖问题已通过安装 requirements 中的 `jsonschema` 解决。过滤失败已确认是既有测试没有控制自己的前置数据；Schema 改动没有增加新的回归失败。
