## 实验前问答

问题 1：API 负向测试的主要目的是什么？为什么不能只测试正常请求？
回答：验证接口收到错误、缺失、越界或不符合业务规则的请求时，能否正确拒绝、给出合理响应且不产生错误数据。正常请求只能证明正确输入可用，不能证明接口健壮性。

问题 2：当前 booking payload 哪些字段是核心必填字段？逐个删除时合理预期是什么？
回答：`firstname`、`lastname`、`totalprice`、`depositpaid`、`bookingdates.checkin` 和 `bookingdates.checkout` 是核心必填字段，`bookingdates` 也是必填对象；逐个删除时理想预期为 `400 Bad Request` 和明确错误信息。实际行为必须单独记录，不能把实际的 `500` 改成预期。

问题 3：如果缺失字段后接口仍返回 `200` 并创建 booking，测试应该怎么处理？
回答：断言仍应失败并识别为必填校验缺失；同时在 `try/finally` 中提取动态 `bookingid` 并清理，避免断言失败跳过清理，污染后续测试。

## 学习记录

今天理解了：

负向测试验证错误输入的拒绝方式、错误信息和数据安全性；缺陷预期不能因当前实现返回 500 或 200 而被改写。

它解决的问题：

发现必填字段校验缺失、错误处理不规范和错误请求产生脏数据等风险，并让这些风险能稳定回归。

我实际如何使用它：

新增 `test_invalid_payloads.py`，参数化删除 7 个 booking 必填字段，预期统一为 400；使用 `deepcopy` 保持每个 payload 独立，并在 `finally` 中清理接口错误返回 200 时可能产生的 booking。

遇到的问题：

本地接口对 7 个缺失字段场景均返回 `500 Internal Server Error`，而不是合理的 `400 Bad Request`。

根因或当前假设：

被测服务缺少统一的请求校验和错误映射；当前学习范围只记录并回归该服务行为，不直接修改被测服务。系统 Python 没有 pytest，验证使用项目 `.venv`。
