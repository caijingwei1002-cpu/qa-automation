## 学习记录

今天理解了：BFF 返回 `200/500` 都只能说明代理链路得到响应；只有证明 resolved target 由预期下游服务提供，后面的状态码、字段和业务数据才有资格进入目标 API 契约判断。

它解决的问题：避免把错误端口、旧服务、Mock、外部 Express 或其他项目的响应误报为目标 Room/Booking 缺陷，也避免为了补认证而越过只读边界。

我实际如何使用它：为 Room/Booking 分别设计 default 与 override 用例，记录 resolved target、BFF 可达、下游监听、服务身份、认证前置和停止层；当前只保留源码与既有环境事实。

遇到的问题：UI/BFF 未启动，Room 默认下游身份不符，Booking 下游无监听且没有现成 token。

根因或当前结论：BFF live 勘察在最早前置层受阻；Room 深层证据为 `SERVICE_IDENTITY_MISMATCH`，Booking 深层证据为 `DOWNSTREAM_UNAVAILABLE` 与 `AUTH_PRECONDITION_UNMET`。契约层今天没有进入。
