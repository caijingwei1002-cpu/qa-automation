## 实验前问答

问题 1：`RestfulBookerClient` 和 `BookingClient` 应该分别负责什么？
回答：`RestfulBookerClient` 负责通用 HTTP 基础设施，例如 base_url、timeout、默认 headers、URL 拼接、HTTP 方法、params/json、Token/Cookie 和网络异常处理；`BookingClient` 负责 booking 领域动作，例如创建、查询、更新、部分更新和删除。三层边界是：通用 Client 负责怎么发请求，领域 Client 负责对 booking 做什么，测试负责验证结果。

问题 2：`BookingClient` 至少应该提供哪些 booking 领域方法？
回答：至少提供 `create_booking`、`get_booking`、`get_bookings`、`update_booking`、`partial_update_booking` 和 `delete_booking`，分别对应 POST /booking、GET /booking/{id}、GET /booking、PUT /booking/{id}、PATCH /booking/{id} 和 DELETE /booking/{id}。鉴权 Token 以后可由独立的 `AuthClient` 负责。

问题 3：领域方法应该返回原始 `Response`，还是直接返回 JSON 或 bookingid？
回答：当前阶段返回原始 `Response` 更合适。这样测试仍能验证状态码、headers、JSON 结构、业务字段和错误响应，避免领域 Client 吞掉 HTTP 信息或因直接读取 `bookingid` 把接口错误变成难定位的 `KeyError`。以后可以额外增加返回 bookingid 的辅助方法，但不替代核心方法的原始响应。

## 学习记录

今天理解了：领域客户端（domain client）位于通用 HTTP Client 和测试之间，用 booking 语义封装 endpoint；它让测试表达创建、查询、更新和删除 booking 的业务动作。

它解决的问题：避免测试重复知道 `/booking` 路径、HTTP 方法和参数组织方式，同时不把状态码、响应结构和业务预期隐藏在领域 Client 中。

我实际如何使用它：新增 `BookingClient`，提供 `create_booking`、`get_bookings`、`get_booking`、`update_booking`、`partial_update_booking` 和 `delete_booking`；booking 测试通过领域方法发送请求，认证和健康检查仍使用通用 `api_client`。

遇到的问题：初始接入时部分 booking 测试仍直接使用通用 `api_client`，并且 Fixture 的导入顺序需要调整。

根因或当前假设：领域 Client 只有被 booking 测试实际调用，才能形成有效的职责边界；Fixture 必须先配置项目路径，再导入 `src` 下的客户端模块。
