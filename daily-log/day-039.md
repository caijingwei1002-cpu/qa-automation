## 学习记录

今天理解了：动态 ID 让多个 API 请求形成因果关联；GET 的 `200` 只能证明查询请求成功，字段与 payload 一致才进一步证明创建后的数据链路符合预期。

它解决的问题：避免固定 ID 命中历史数据、其他测试数据或不存在的资源，也避免只看状态码造成假通过。

我实际如何使用它：在 `test_booking_flow.py` 中从 `create_response.json()["bookingid"]` 读取本次 ID，再拼接 `/booking/{booking_id}` 发起 GET，并逐项比较字段。

遇到的问题：代码审查发现 `BOOKING_URL` 被使用但没有定义。

根因或当前假设：这是脚本执行配置问题，会在请求前触发 `NameError`；补充 `BOOKING_URL` 后目标测试通过。若将来出现字段不一致，还需先排除取错 ID、环境污染和比较逻辑错误，再判断产品一致性问题。
