## 实验前问答（回溯补充）

关联知识点：认证接口、HTTP 与业务结果分层、凭据管理和 Token 脱敏。

**问题 1：** 为什么无效凭据不能只根据 HTTP 状态码判断？
**参考回答：** 本地接口对有效和无效凭据都返回 200，必须检查业务字段：成功有非空 `token`，失败有 `reason == "Bad credentials"`。

**问题 2：** Token 测试为什么不能把 Token 打印出来？
**参考回答：** Token 是敏感认证材料，日志和报告可能被长期保存或共享；测试只需断言它存在、是非空字符串，不应暴露具体值。

## 学习记录

今天理解了：
HTTP 状态码只说明请求在 HTTP 层的处理结果，认证是否成功要根据响应业务字段判断；本地 Restful Booker 对有效和无效凭据都返回 200。

它解决的问题：
避免把 `200` 误判为登录成功，也避免把认证失败误归因为 HTTP 层错误。

我实际如何使用它：
在 `test_auth.py` 中通过参数化覆盖有效和无效凭据，分别断言非空 `token` 与 `reason == "Bad credentials"`；使用 `api_base_url`、`request_timeout_seconds` 和 `auth_credentials` fixture，避免直接导入 `conftest.py`。

遇到的问题：
初版从 `conftest.py` 导入不存在的常量，并且测试代码曾重复追加一份。

根因或当前假设：
`conftest.py` 应通过 pytest fixture 注入，而不是作为普通配置模块导入；重复定义同名测试函数会覆盖前一份定义。修正后目标测试和 API 全量回归均通过。
