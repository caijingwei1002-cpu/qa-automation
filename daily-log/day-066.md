## 实验前问答

问题 1：登录前置、点击结账和验证订单成功分别放在哪里？
回答：登录前置放 fixture；点击结账是 Page Object 或测试中的业务动作；订单成功断言留在测试主体中。

问题 2：正常登录和错误密码测试是否使用 `logged_in_page`？
回答：不使用。它们本身要验证登录行为，使用已登录 fixture 会跳过被测动作，错误密码场景也与已登录前置矛盾。

问题 3：如何避免两个结账测试互相污染？
回答：使用 function scope 的独立 BrowserContext/Page；每条测试自己建立购物车状态，不把 fixture 当作购物车为空的保证，并考虑服务器端账号状态隔离。

## 学习记录

今天理解了：UI 测试的职责分层与 API 测试一样重要；fixture 提供稳定前置，Page Object 提供动作接口，测试主体证明当前业务结果。

它解决的问题：减少重复登录步骤和维护范围，同时避免共享 fixture 隐藏业务动作或断言，使失败更容易定位到 setup、页面动作或业务结果。

我实际如何使用它：在 `conftest.py` 中新增 `logged_in_page`，只执行登录并等待 inventory URL；在结账测试中从已登录商品页开始，保留购物车、结账和订单完成断言；登录专项继续使用基础页面。

遇到的问题：完整回归第一次在登出测试中找不到 Logout，`get_by_role("link", name="Logout")` 等待超时。

根因或当前假设：页面 ARIA snapshot 显示 Logout 是 button，不是 link；原定位器角色假设错误。改用 button 定位并等待可见后，登出专项通过，完整回归 22 条全部通过。
