## 实验前问答

问题 1：提交前只剩几分钟时，为什么先跑 smoke？
回答：smoke 按关键业务风险选择，快速回答服务、鉴权和核心链路是否可用；完整 regression 的覆盖更广，时间足够时再运行。

问题 2：`smoke` marker 表达什么？
回答：表达测试的重要性和用途，不是单纯表达执行速度；快速但非关键的边界测试不一定属于 smoke。

问题 3：smoke 通过但 regression 失败，如何分类？
回答：先看覆盖范围差异，再检查测试代码和环境稳定性；只有在前置条件、请求和预期都正确且稳定复现时，才有充分依据判断为产品缺陷。

问题 4：为什么要注册 marker 并启用 strict markers？
回答：未注册或拼写错误的 marker 可能只产生 warning，导致关键测试从 smoke 集合中悄悄漏掉；严格模式会把它变成明确失败。

问题 5：Ruff 通过能证明什么，不能证明什么？
回答：只能证明当前启用的静态规则和格式检查通过，不能证明 API 的 HTTP 响应、业务断言、服务状态或资源生命周期正确。

## 学习记录

今天理解了：smoke 是按关键风险选择的可用性子集，完整 `pytest` 是默认 regression；Ruff lint/format 负责代码形态，不能替代运行时测试。

它解决的问题：提交前可以用小而关键的集合快速发现服务或核心业务阻断，同时保留完整回归发现边界和异常问题；严格 marker 和项目范围 Ruff 让入口结果可解释、可复现。

我实际如何使用它：把 health、authentication、full lifecycle 标记为 smoke，使用 `pytest --markers` 和 `--collect-only -m smoke` 核对集合，再按 `ruff → smoke → pytest` 执行质量检查。

遇到的问题：第一次 smoke 因本地 Restful Booker 未监听 `127.0.0.1:3001` 而连接被拒绝；项目范围 Ruff 随后发现 7 个导入排序问题和 9 个历史格式差异。

根因或当前假设：服务未准备好时测试尚未进入业务断言；静态检查问题属于项目基线格式和导入组织，不是 API 行为缺陷。启动服务并完成限定范围的 Ruff 修复后，目标检查和完整回归均通过。
