## 实验前问答

问题 1：为什么要把 `base_url`、超时和公共 headers 集中到 API Client，而不是每个测试重复配置？
回答：集中配置可以统一请求行为、减少重复和维护成本，避免端口、超时或公共请求头变化时多个测试文件漏改或配置不一致。测试只表达业务动作，例如 `client.get_booking(booking_id)`，而不是重复拼接 HTTP 请求。

问题 2：API Client 应该负责哪些内容？哪些业务断言应该继续保留在测试中？
回答：API Client 负责 base URL、timeout、公共 headers、URL 拼接、HTTP 方法、JSON 请求体、Token/Cookie 传递、通用响应处理和请求错误信息整理；测试继续负责具体场景的状态码、响应字段和业务结果断言。核心边界是：Client 负责“怎么请求”，测试负责“结果是什么”。

问题 3：通用请求失败时，错误信息至少应该包含哪些关键信息，才能方便定位？
回答：至少包含 HTTP 方法、请求 URL、状态码、timeout 配置、响应体安全摘要和实际查询参数；请求 JSON 只能记录非敏感字段，并且必须对 Token、Cookie、密码等敏感信息脱敏。

## 学习记录

今天理解了：API Client 是 HTTP 传输层边界，统一处理 base URL、timeout、公共 headers、URL 拼接和请求发送；测试保留业务动作编排和结果断言。

它解决的问题：减少每个测试重复配置 HTTP 请求造成的维护成本和配置漂移，并让网络异常包含可定位上下文，同时避免 Client 替业务场景决定状态码。

我实际如何使用它：在 `src/api_client.py` 创建 `RestfulBookerClient`，通过 `conftest.py` 的 `api_client` fixture 注入所有 API 测试；测试使用 `api_client.get/post/put/patch/delete`，继续断言状态码、响应体和业务规则。

遇到的问题：初始 Client 放在了错误位置且没有被测试使用；错误摘要还需要避免带出响应中的敏感字段。

根因或当前假设：目标契约规定 Client 位于 `src/api_client.py` 并作为公共请求入口；HTTP 状态码仍属于测试场景预期，因此 Client 不统一调用 `raise_for_status()`，而是只包装网络层异常并对摘要脱敏。
