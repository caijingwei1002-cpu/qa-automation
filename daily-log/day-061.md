## 实验前问答

问题 1：为什么 Mock `requests.request`？
回答：验证 Client 与底层 HTTP 库之间的调用契约，检查方法、URL、参数和 timeout，而不把网络环境或服务状态混入测试。

问题 2：网络异常应该如何处理？
回答：如果 Client 约定统一异常边界，就把底层 `Timeout`、`ConnectionError` 转换为 `ApiRequestError`；错误消息应包含方法、URL、timeout 和异常类型，同时保留原始异常并隐藏 Token、密码等敏感信息。

问题 3：如何证明请求之间没有状态污染？
回答：第一次请求传入临时 Header 和 Token，第二次不传这些值；检查两次实际调用的 Header，并确认 `default_headers` 与调用方原始字典都未被修改。

## 学习记录

今天理解了：Mock 是控制依赖的手段，可以把 Client 的传输层行为与真实网络、服务数据和服务可用性分离开。

它解决的问题：直接请求真实服务时，timeout 是否传递、URL 是否拼接正确、异常是否统一转换和 Header 是否污染很难被单独定位；服务没启动还会让这些单元行为测试无法运行。

我实际如何使用它：在 `test_api_client.py` 中 patch `src.api_client.requests.request`，返回假的 Response 或抛出指定网络异常，再检查 Mock 的调用参数、包装异常和连续请求的 Header 状态。

遇到的问题：初始测试虽然 `4 passed`，但第一个测试没有检查 Mock 调用参数，第二个测试只创建了未使用的 `message`；随后 Ruff 还提示导入和格式问题。

根因或当前假设：测试骨架中的注释没有转化为可执行断言，测试通过不能自动证明契约已被验证。补齐 `assert_called_once_with`、错误消息断言和敏感信息断言后，再用 Ruff format 修正格式。
