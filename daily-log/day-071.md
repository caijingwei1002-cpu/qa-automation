## 学习记录

今天理解了：服务身份不是端口号或状态码，而是端口到 PID、进程来源、版本配置和 HTTP 行为组合形成的证据链。

它解决的问题：避免把其他项目的响应、错误版本的行为或错误 context path 归因给目标产品，也避免在环境不可信时生成污染性的缺陷回归证据。

我实际如何使用它：先用 `netstat`、进程元数据和只读 GET 建立 `3001` 的身份结论，再根据安全边界决定是否允许恢复默认端口；本日没有跨过未授权的进程处理边界。

遇到的问题：默认 `3001` 被其他 `restful-booker` Node/Express 项目占用，Platform Room 默认运行基线未能恢复。

根因或当前结论：PID `29528` 的命令行和父进程指向外部 Node 项目；`/room/actuator/health` 与 `/room/` 都返回 Express `404`。这证明当前端口不是 Platform Room，但没有证明 Platform Room 在默认 `3001` 下无法启动，也没有完成删除后 `500` 的正式回归。
