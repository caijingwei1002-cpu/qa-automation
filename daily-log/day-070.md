## 学习记录

今天理解了：测试基线不是“服务能启动”这么简单，而是源码版本、依赖运行时、端口/context path、认证、契约和运行命令共同组成的被测事实集合。

它解决的问题：避免请求打到错误进程或错误版本，避免把连接失败和认证失败误判成业务缺陷，也避免把 POST 成功或资源存在误当成 Room 与 Booking 已经正确关联。

我实际如何使用它：先确认源码，再健康检查和独立认证；随后使用本次创建的动态 Room/Booking ID 完成查询与关联断言，并在 finally 中按依赖顺序清理。

遇到的问题：完整 Maven 构建的 Room 集成测试和默认 Room 服务都无法绑定 `3001`。

根因或当前假设：`3001` 被 `D:\qa-automation-targets\restful-booker` 的 Node 进程占用；Room 删除后查询 `500` 与 `RoomDB.query()` 空 ResultSet 处理不当有关，但具体 JDBC 异常类型未直接作为本轮证据确认。
