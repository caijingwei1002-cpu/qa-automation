## 实验前问答

问题 1：为什么生命周期测试必须使用 POST 返回的动态 `bookingid`，而不能写死一个 ID？
回答：动态 ID 能证明后续 GET、PUT、DELETE 针对的是当前测试刚创建的资源；写死 ID 会依赖环境数据，可能不存在、属于其他测试或内容已变化，导致污染和不稳定。

问题 2：为什么不能只在最后断言删除后 GET 返回 404？
回答：生命周期测试需要验证每个状态转换都成功发生。逐步断言能在创建、查询、更新或删除阶段立即暴露并定位失败，最终 404 不能证明前面的步骤都成功。

问题 3：如果 PUT 失败，测试如何保证仍然清理 booking？
回答：把清理放在 `try/finally` 或 `yield fixture` 的 teardown 中，无论中途哪个断言失败，清理逻辑都会继续执行。

## 学习记录

今天理解了：接口生命周期测试不是把多个请求简单串起来，而是验证同一动态资源在创建、读取、更新和删除之间的状态转换。

它解决的问题：证明资源 ID 关联正确、每一步状态真的发生变化，并让失败定位到具体生命周期阶段，而不是只看到最终结果。

我实际如何使用它：使用数据工厂生成独立 payload，保存 POST 返回的动态 ID，逐步断言 POST/GET/PUT/GET/DELETE/GET 结果，并在 `finally` 中按资源状态清理。

遇到的问题：最初版本在创建响应字段断言之后才保存 booking ID，并用 `deleted` 标志决定是否清理，存在断言失败后遗漏资源的风险。

根因或当前假设：清理线索和清理状态不应依赖正常流程走完；修改后先提取 ID，清理时重新查询资源，只有确认 404 才视为完成。
