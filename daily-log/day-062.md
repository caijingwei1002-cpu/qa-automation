## 实验前问答

问题 1：Mock Client 单元测试能证明什么，不能证明什么？
回答：它能证明 Client 构造 URL、方法、参数、timeout、Header 和异常转换等传输层逻辑；不能证明真实网络、服务可用性、真实认证或业务响应契约。

问题 2：为什么只断言完整敏感值消失不够？
回答：如果规则只替换到第一个空格，完整字符串虽然消失，敏感值主体仍会残留。因此安全断言必须同时检查主体片段消失，并保留非敏感诊断信息。

问题 3：`403` 与超时的失败证据如何区分？
回答：`403` 表示收到了 HTTP Response，应保留状态码和安全正文；超时可能没有 Response，应明确标记无响应并保留 Timeout 类型和 timeout 配置。

问题 4：摘要规则需要先澄清哪些安全边界？
回答：确认哪些字段必须隐藏、URL 参数和请求体是否可记录、响应正文最大长度、是否保留 request ID/trace ID，以及 4xx、5xx、超时和连接失败的摘要格式。

问题 5：为什么不能先截断再脱敏？
回答：截断可能切断敏感字段结构，使规则无法识别完整值；最终日志大小应按脱敏后的正文限制。

问题 6：如何证明脱敏没有修改原 Response？
回答：在生成摘要前保存 `text`、`content` 和 `headers`，生成摘要后逐项比较原对象，同时断言安全摘要保留非敏感信息。

## 学习记录

今天理解了：失败摘要必须在安全边界内提供足够诊断信息；敏感值的完整结构边界决定脱敏是否可靠。

它解决的问题：原有规则把空格当成敏感值结束位置，导致 `Bearer abc def 456` 只替换 `Bearer`，主体仍进入摘要；只检查完整值消失会让这种部分泄漏假通过。

我实际如何使用它：先用普通 `403` 和异常携带 Response 的测试证明摘要入口，再用双引号 JSON、单引号 `repr`、Cookie 多段值和多词 `params` 覆盖结构边界；同时验证非敏感诊断、截断、异常链和原始对象不变。

遇到的问题：初版测试结果为 `10 passed, 6 failed`；失败集中在多词敏感值主体仍出现在摘要中。Ruff 后续还提示正则字符串和测试字面量格式问题。

根因或当前假设：`_redact_sensitive()` 原正则的值部分使用了不允许空格的字符类，只能匹配第一个片段。改为区分带引号和无引号值的结构匹配后，目标测试和全量回归通过；当前规则仍只覆盖已登记字段和已建模序列化形式。
