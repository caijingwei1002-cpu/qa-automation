## 实验前问答

问题 1：如果创建成功后还没保存 bookingid 就断言失败，会有什么风险？
回答：后续无法准确定位和删除当前资源，可能留下脏数据；应在创建成功后先保存动态 ID，再做其他断言，并用 finally 兜底清理。

问题 2：配置模块、fixture、API Client 和测试函数各自负责什么？
回答：配置模块读取、清洗和校验环境配置；fixture 准备并注入依赖；API Client 负责 URL 拼接、headers 和 HTTP 传输；测试函数描述场景并做业务断言。请求目标属于配置层。

问题 3：如何确认环境变量没有真正切换到新服务？
回答：依次检查进程环境变量、Settings 解析值、fixture 传入值、Client 的 base_url/timeout 和实际请求 URL，定位配置在哪一层被旧值覆盖。

## 学习记录

今天理解了：配置分层要求把环境变量读取、默认值、清洗、类型转换和合法性校验集中在 `settings.py`；fixture 只注入已经可信的 `Settings` 值，Client 只负责传输，测试保留业务预期。

它解决的问题：避免每个 fixture 或测试重复解析环境变量，防止环境切换时出现旧地址、错误 timeout 或导入时缓存，并让配置错误在发送 HTTP 前快速暴露。

我实际如何使用它：在 `Settings` 中实现 URL 校验和 `RESTFUL_BOOKER_TIMEOUT_SECONDS` 的有限正浮点校验；让 `settings`、`api_base_url` 和 `request_timeout_seconds` fixture 逐层传递配置；用单元测试覆盖默认值和边界，用链路测试验证 `api_client.base_url` 与 `timeout`，不发送 HTTP。

遇到的问题：第一次运行使用系统 Python，因未安装 pytest 失败；配置链路完成后全量回归还暴露了过滤测试依赖 `Jim/Brown` 固定数据的问题；timeout 测试修改过程中还出现了同名测试覆盖参数化测试的问题。

根因或当前假设：运行命令没有使用项目虚拟环境；过滤测试假设服务重启后仍保留预置记录；同名函数让后定义覆盖前定义，导致参数化用例未被收集。改用 `.venv`、测试自建 booking 并在 finally 清理、重命名动态读取测试后，问题消失。
