## 实验前问答

问题 1：POST /booking 超时后，能否确定预订没有创建？
回答：不能。超时只表示客户端在规定时间内没有收到响应；请求可能未到达、仍在处理、服务端失败，或已经创建成功但响应丢失，所以状态是结果未知。

问题 2：哪些请求通常适合重试？
回答：GET 通常幂等，使用相同内容的 PUT 通常幂等，DELETE 的最终资源状态通常幂等；POST 默认不幂等，只有服务端提供幂等键或唯一业务标识时才可能安全重试。

问题 3：一个有边界的重试策略需要哪些约束？
回答：限制最大尝试次数，只重试明确的临时故障，等待使用指数退避和抖动等策略，并根据操作的副作用和去重能力决定是否允许重复执行。

问题 4：如何判断重试没有制造重复预订？
回答：不能只看第二次请求成功；还要观察实际请求次数、服务端业务执行次数、最终资源数量以及幂等键是否生效。当前最小策略直接禁止普通 POST 自动重试。

## 学习记录

今天理解了：是否重试不取决于请求有没有报错，而取决于故障是否暂时、操作是否幂等、重复副作用是否可控，以及策略是否有明确上限。

它解决的问题：网络超时后的结果可能未知；如果对普通 POST 盲目重试，第一次请求可能已经创建资源，第二次请求会制造重复预订或其他副作用。有界策略让调用次数和等待位置都可以被测试直接观察。

我实际如何使用它：让 request_action 作为可注入动作，GET 只对 Timeout 和 ConnectionError 在 max_attempts 内重试；POST 无幂等键时只调用一次；用 Mock 记录调用次数和 sleep 次数，并补充非正 max_attempts 的参数边界。

遇到的问题：第一次 API 全量回归因本地 3001 服务未启动而出现连接拒绝，测试等待时间较长。

根因或当前假设：验证 runner 原先只执行 pytest，没有服务准备步骤。增加健康检查和按需启动后，服务未运行时可以先完成环境恢复；如果启动命令、工作目录或健康端点配置错误，runner 会提前失败并把原因写入证据。
