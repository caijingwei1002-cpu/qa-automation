## 实验前问答

问题 1：为什么 `assert response.status_code != 200` 会让 `201` 或 `500` 造成负向测试假通过？
回答：它只证明状态码不是 200，无法证明接口按契约以 400、403 或其他指定错误方式失败；201 说明资源仍被创建，500 说明服务端崩溃，二者都可能被错误判定为通过。

问题 2：哪些信息应该放进通用 `assert_error_response()`，哪些必须留在具体测试中？
回答：helper 负责精确状态码、错误体非空、可选通用文本和统一失败消息；具体测试负责构造业务输入、选择预期状态和业务字段/错误码，不能把所有业务规则塞进万能 helper。

问题 3：预期 400、实际 500 且响应体为 Internal Server Error 时，失败消息至少应包含什么？
回答：至少包含场景或参数化 case、预期状态码、实际状态码和响应体摘要，才能快速区分业务校验失败、错误状态分级问题和服务端异常。

## 学习记录

今天理解了：

负向测试要验证规定的错误状态码和可解释错误体，而不是把所有非 200 响应都视为成功；重复机制应抽取到 helper，业务原因仍由具体测试表达。

它解决的问题：

统一状态码、响应体和文本匹配的失败信息，避免不同负向测试各自实现导致断言标准漂移，也避免 `201`、`500` 等结果制造假通过。

我实际如何使用它：

新增 `tests/assertions.py`，实现状态码范围保护、精确状态码、非空响应体、可选错误文本和压缩响应摘要；将无 Token PUT 和重复 DELETE 两个稳定负向场景迁移到该 helper。

遇到的问题：

服务重启后全量过滤测试中 `firstname=Jim` 和 `lastname=Brown` 两组找不到数据，导致 2 条失败。

根因或当前假设：

已确认是既有测试依赖预置数据而没有控制自己的前置条件；后续应由测试创建唯一 booking 并在 finally/yield 中清理。该问题不是本日 helper 造成的。
