## 实验前问答

问题 1：删除 booking 后，为什么还要用同一个动态 `bookingid` 再次 GET？
回答：删除后必须用同一个动态 `bookingid` 再次 GET，才能证明删除的是本次测试刚创建的资源，并验证资源确实已经不可查询。只看 DELETE 响应可能出现接口返回成功但资源仍存在的假通过。

问题 2：删除测试除了验证 DELETE 本身成功，还应该继续验证哪些结果？
回答：删除测试除了验证 DELETE 成功，还要验证删除后的 GET 返回资源不存在对应的状态/响应，并确认查不到的正是本次动态 `bookingid`。如果契约规定返回 `404`，就应明确断言 `404`。

问题 3：
为什么要创建后删除本次测试自己的资源，而不是使用固定 `bookingid`？
回答：
固定 `bookingid` 可能不存在、属于历史数据、被其他测试修改或删除，也可能在不同环境中指向不同内容。动态 ID 能保证测试数据归属明确、测试之间更独立，并避免误删共享环境中的其他数据。

## 学习记录

今天理解了：资源测试应覆盖从创建、操作到删除、删除后确认的完整生命周期；DELETE 返回成功只是即时结果，二次 GET 返回 `404` 才补充了资源已不可读取的后置证据。

它解决的问题：避免测试数据长期污染共享环境，也避免把 DELETE 的成功状态误当作资源已经消失，形成假通过。

我实际如何使用它：先 POST 创建本次测试自己的 booking，读取动态 `bookingid`，使用 Token 执行 DELETE，断言 `201`；再用相同 ID GET，断言 `404`。另外验证了同一资源重复删除返回 `405`。

遇到的问题：本日实现未遇到阻塞。

根因或当前假设：本地 Restful Booker 契约规定已删除资源再次 GET 返回 `404`，不存在的资源重复 DELETE 返回 `405`；这些状态码应以当前接口契约为准，不能脱离契约套用通用猜测。
