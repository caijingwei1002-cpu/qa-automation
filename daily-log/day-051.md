## 实验前问答

问题 1：为什么 `200` 和 `"200"`、`true` 和 `"true"` 对 API 契约来说不是同一种输入？
回答：API 契约同时约束值和 JSON 数据类型；前两者分别是 number 和 boolean，带引号后都是 string。服务端自动转换只能说明实现容忍错误输入，不能证明请求符合契约。

问题 2：如果错误类型请求返回 200 并生成 bookingid，测试还必须做什么？
回答：保留 400 业务预期并报告接口错误接受请求，同时提取动态 bookingid，在 finally 中清理意外资源；必要时可在删除前回查服务端是否持久化或转换了错误值。

问题 3：为什么 `"not-a-date"` 是格式错误，而 `12345` 是类型错误？
回答：契约要求日期为 string 时，`"not-a-date"` 的类型仍正确，只是内容不符合日期格式；`12345` 是 number，在讨论格式之前就已经违反类型约束。类型错误、格式错误和 null 约束应分开测试。

## 学习记录

今天理解了：

API 输入契约不仅约束值的业务含义，也约束 JSON 类型；类型正确但内容非法属于格式错误，类型本身不符则属于类型错误。

它解决的问题：

发现服务端静默类型转换、缺少请求校验和错误数据持久化风险，让调用方错误可以被稳定回归而不是被 200 响应掩盖。

我实际如何使用它：

新增 `test_invalid_types.py`，从合法数据工厂出发，用字段路径参数化覆盖 `totalprice="200"`、`depositpaid="true"` 和 `bookingdates.checkin=12345`，统一预期 400，并保护意外资源清理。

遇到的问题：

本地接口对三组错误类型均返回 200、创建 booking 并转换输入：字符串价格变成数字、字符串布尔值变成布尔值、数字日期变成 `1970-01-01`。

根因或当前假设：

当前可确认的是服务端缺少严格类型拒绝并执行了隐式转换；数字日期可能被当作时间值处理只是根据响应提出的假设，未通过被测服务源码确认。
