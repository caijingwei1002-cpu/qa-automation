## 实验前问答

问题 1：`22 passed` 或 `90 passed` 能证明什么，不能证明什么？
回答：只能证明当前环境、当前代码、实际收集并执行的测试本次通过；不能证明未覆盖场景、测试设计正确、失败分支、隔离稳定性、跨环境行为或产品整体没有问题。

问题 2：缺失 `firstname` 时为什么不能只凭断言把 Expected 写成 400？
回答：400 必须有 API 契约、需求或明确团队约定支持；测试代码里的 `assert response.status_code == 400` 只能说明测试作者写了这个预期。若契约规定 422，应遵循 422；没有正式依据就把状态码预期标为未知。

问题 3：如何构造这个负向场景？
回答：使用已验证成功的完整 payload，仅删除 `firstname` key；不改为空字符串、`null` 或其他字段，保持请求方法、URL、请求头、认证和其余值不变。

问题 4：为什么要使用 `--runxfail`？
回答：普通 `xfail` 会把已知失败折叠成 `xfailed`，不展示真实断言差异；`--runxfail` 会显式执行断言，得到 `Expected 400 / Actual 500` 和 `1 failed`，便于诊断。

## 学习记录

今天理解了：缺陷报告不是把测试失败改写成结论，而是把契约预期、单变量请求、原始响应、持久化状态、执行范围和未知项串成可复核证据链。

它解决的问题：避免把当前实现或开发口头判断当作需求，避免把一次通过当作系统无缺陷，也避免把连接拒绝、未覆盖场景或推测的服务端根因写入 Actual Result。

我实际如何使用它：从合法 booking factory 数据出发只删除 `firstname`，用 `--runxfail` 展开已知失败，记录 HTTP 500 和响应体；报告引用实际命令与证据文件，同时保留 Expected 400 的正式契约依据尚未证实这一限制。

遇到的问题：普通目标运行只得到 `xfailed`，服务未启动时还出现 `WinError 10061`；复盘中一度把已执行的全量回归误写成未执行。

根因或当前假设：`xfail` 隐藏了真实断言，需要 `--runxfail` 诊断；连接拒绝来自服务 readiness；全量回归实际已经由学习者提供并由统一验证器复跑确认。HTTP 500 的服务端内部根因仍未由日志或源码确认。
