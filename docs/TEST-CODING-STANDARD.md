# 测试代码编写与审查规范

适用于 Day 56 起的新代码和触及的旧代码。历史代码渐进整理，不能以格式通过代替行为正确。

## 职责与可读性

- 测试名表达场景与预期，例如 `test_filter_excludes_nonmatching_bookings`。
- 测试主体按准备、操作、断言组织；一个测试围绕一个业务目的，可含多个相关断言。
- fixture 管前置、隔离和资源生命周期；Client/Page Object 管动作；业务预期保留在测试中。
- `assert_*` helper 只验证传入数据。需要发送请求的流程函数使用明确动作名称。
- 共享函数标注参数、返回类型；不为了缩短测试而创建万能 helper 或 BasePage。
- 重复的公共机制统一维护；相似但不同的业务规则不强行合并。
- 注释解释约束和原因，教学长文进入 LEARNING-NOTES.md。自动格式化处理换行与导入。

## 数据与异常路径

- 每条测试创建自己的数据，不依赖 Jim/Brown、固定 ID 或执行顺序。
- 创建响应一到就提取并登记资源 ID，再做可能失败的断言；清理覆盖中途失败及已删除情况。
- 清理只操作测试拥有的资源，核实最终状态；清理失败与业务失败分别保留诊断信息。
- 业务断言不吞异常；不使用 catch-all、宽泛状态码集合或盲目重试制造通过。
- xfail 记录依据、已知行为和移除条件；strict 只约束意外通过，不能限制失败原因。
- 未知响应、网络故障、鉴权和清理失败必须显式暴露。只设置 raises=AssertionError 仍可能过宽。
- 预期必须有契约或已确认业务规则；教学假设需标注，不能直接当作产品缺陷。

## UI 与验证

- 使用稳定定位和条件等待；避免固定 sleep。登录专项直接验证登录，其他测试可复用已登录前置。
- helper 重构不能隐藏关键业务断言；UI 与 API 分层验证同一业务时解释各层价值。
- 共享机制修改需目标测试和受影响项目回归；清理、异常转换需受控故障验证。
- 记录命令、结果、失败分类与证据，不删除断言或扩大 xfail 范围以消除失败。

## 日常审查

每次编码由学习者先自审，教练给出行号、影响、修改方向；学习者修改后复审。
检查命名、职责、隔离、清理、断言有效性、重复、诊断和预期依据。
见 templates/code-review.md；工具只提供格式与静态信号，不能替代审查。

从 Day 77 起，编码课的实践证据必须指向学习者参与实现的代码或测试文件；验证证据必须包含测试收集与实际执行结果。设计矩阵、README 和 `git diff --check` 可以作为补充证据，但不能单独证明编码或自动化执行能力。教练保存文件、修复代码和学习者独立实现分别记录。
